1. Objective
Build a production-quality Flutter e-commerce catalogue app, ShopSphere, that consumes the
DummyJSON REST API. The app lets a user sign in, browse and search products, view product details,
manage a cart, and view their profile. Through this single project we will assess the following areas:
Area
What we look for
UI / UX design
Visual polish, consistent theming (Material 3), spacing & typography, intuitive flows,
meaningful loading / empty / error states, micro-interactions, accessibility.
State management
Predictable, well-scoped state using one solution (BLoC/Cubit, Riverpod or Provider).
No business logic inside widgets.
Clean architecture
Clear separation of presentation, domain and data layers; dependency inversion;
dependency injection; feature-first, readable folder structure.
API integration & error handling
Typed models, a dedicated network layer, auth token handling, timeouts, mapping of
exceptions to user-friendly failures, retry flows.
Unit testing

dependencies.
Git practices

built.
Responsive layouts
Layouts that adapt gracefully across phones, tablets, portrait and landscape.

3.1 Splash & Authentication
 [Must] Splash screen that checks for a stored session and routes to Home or Login.
 [Must] Login screen with username & password fields, inline validation (empty fields, min length),
password visibility toggle, and a loading state on the submit button.
 [Must] Call POST /auth/login; store the access & refresh tokens securely (e.g.
flutter_secure_storage).
 [Must] Show a clear message for invalid credentials (API returns HTTP 400 “Invalid credentials”).
 [Bonus] Automatically refresh an expired access token via POST /auth/refresh using an HTTP
interceptor, then retry the original request.
3.2 Home — Product List
 [Must] Display products in a responsive grid/list showing thumbnail, title, price, discount and rating.
 [Must] Pagination with infinite scroll using limit & skip (page size 20); show a footer loader and stop
when all items are loaded.
 [Must] Pull-to-refresh.
 [Must] Horizontal category chips loaded from the API; selecting one filters the list.
 [Must] Search bar with debounce (approx. 400 ms) using the search endpoint.
 [Must] Sort options: price low-to-high / high-to-low, rating, title.
 [Must] Skeleton / shimmer placeholders during first load; dedicated empty state for “no results”.
3.3 Product Details
 [Must] Image carousel with page indicator, title, brand (absent on some products, so handle null), price
with discount, rating, stock status, description, and the list of customer reviews.
 [Must] “Add to cart” with quantity selector; disable it when the product is out of stock.
 [Must] Handle a non-existent product gracefully (e.g. /products/9999 returns 404).
 [Bonus] Hero animation from list thumbnail to details image.
3.4 Cart & Checkout
 [Must] Add, remove and update item quantity; show subtotal, discount and grand total.
 [Must] Persist the cart locally so it survives an app restart (Hive, Isar, sqflite or shared_preferences).
 [Must] Cart badge on the navigation bar / app bar reflecting item count in real time.
 [Must] “Place order” calls POST /carts/add and shows a success screen; clear the cart on success.
(DummyJSON simulates this — nothing is actually stored server-side.)
3.5 Profile
 [Must] Fetch the signed-in user via GET /auth/me and show avatar, name, email, phone.
 [Must] Logout that clears tokens and local session, then returns to Login.
 [Must] If the API returns 401 (expired token), or token refresh fails with 403, sign the user out with an
explanatory message.

5. Technical Requirements
5.1 Platform & tooling
 Latest stable Flutter & Dart SDK. Mention exact versions in the README (flutter --version).
 Null-safe, lint-clean code: flutter analyze must report zero issues. Use flutter_lints or
very_good_analysis.
 Format code with dart format. No commented-out dead code, no hard-coded secrets.
5.2 Clean architecture
 Organise code feature-first, each feature split into presentation, domain and data layers.
 Domain layer is pure Dart: entities, repository interfaces and use cases, with no Flutter or HTTP
imports.
 Data layer: DTO/models with fromJson/toJson (freezed / json_serializable welcome), remote & local
data sources, repository implementations.
 Use dependency injection (get_it, injectable or Riverpod providers). Widgets never instantiate
repositories.
5.3 State management
 Pick one of: flutter_bloc (BLoC/Cubit), Riverpod or Provider, and use it consistently.
 Model UI states explicitly (e.g. initial / loading / success / empty / failure / loading-more).
 Explain your choice and its trade-offs in the README in 3–5 lines.
5.4 Networking & error handling
 Single configured HTTP client (dio or http) with base URL, connect/receive timeouts and a logging
interceptor in debug builds only.
 Auth interceptor that attaches the Bearer token to protected requests.
 Map low-level exceptions (SocketException, timeouts, 4xx, 5xx, parse errors) to typed domain
Failures; return them via Either / Result or sealed classes.
 Every network-driven screen must have loading, success, empty and error UI with a retry action.
5.5 Responsive layouts
 Use LayoutBuilder / MediaQuery breakpoints. Minimum expectations:
– Compact (< 600 dp): 2-column grid, bottom navigation bar.
– Medium (600–1024 dp): 3–4 column grid, navigation rail.
– Expanded (> 1024 dp / tablet landscape): master–detail list + details side by side.
 No overflow errors (yellow-black stripes) in any orientation or with system font scaled to 1.3×.

5.6 UI / UX expectations

5.7 Unit testing
 Minimum 15 meaningful unit tests, covering at least:
– Repository implementations: success, server failure and network failure paths.
– Use cases (e.g. login, get products, search, cart total calculation).
– State classes (Bloc/Cubit/Notifier) emitting the correct sequence of states (e.g. with bloc_test).
– JSON model parsing using fixture files.
 Use mocktail or mockito. All tests must pass with flutter test; include a coverage summary in
the README (bonus: ≥ 60%).

6.1 Git commits
 Initialise the repository at the start of the assignment and commit as you go. A single “initial commit”
containing the full project will be heavily penalised.

 Add a proper .gitignore (no build/, .dart_tool/, keystores or IDE files committed).
